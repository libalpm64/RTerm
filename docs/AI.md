# AI setup

## OpenAI Secure MCP Tunnel for ChatGPT

1. In [Platform Tunnels](https://platform.openai.com/settings/organization/tunnels), create a private tunnel associated with the intended Platform organization and ChatGPT workspace. All RTerm installers (Windows, macOS Intel and Apple silicon, Linux DEB and portable) bundle the official client; leave the Tunnel client field on Automatic. Only for source builds without an installed client, download the [official tunnel-client](https://github.com/openai/tunnel-client/releases/latest) for this computer. Extract it beside RTerm, put it on `PATH`, or select it in RTerm's tunnel settings.
2. Create a **Restricted** key in [Platform API keys](https://platform.openai.com/settings/organization/api-keys). Give it tunnel runtime access only, using **Tunnels Read + Use** where those permissions are listed separately. The key owner also needs these permissions in the relevant organization. See the [tunnel permissions guide](https://github.com/openai/tunnel-client/blob/master/docs/permissions.md) for the distinction between runtime and management access.
3. Unlock the RTerm vault. Set **Settings → AI → Agent Access** to **Ask permission** or **Unrestricted** to enable tunnel setup. Choose **Ask permission** for desktop approvals. Open **Advanced** at the bottom of the AI tab, enter the tunnel ID, and paste the runtime key into the masked field.
4. Choose **Apply and Connect** in Advanced AI Settings and wait for **Tunnel ready**. For a previously saved profile, you can also choose **AI → Start Agent**, then **Connect OpenAI Tunnel**. You can opt into connecting automatically when you start the agent. Advanced Settings can copy or export the ChatGPT setup instructions, including the tunnel ID. The export contains no API key.
5. In [ChatGPT Plugins](https://chatgpt.com/plugins), add a custom MCP server with **Connection → Tunnel** and select the same tunnel. Choose **No authentication** for the app's MCP authentication option. Workspace permissions control access through OpenAI and RTerm continues to enforce its configured desktop approvals. Install the private plugin and call `list_sessions`; to test execution, use a harmless command on the intended SSH session and check its exit code.

The local MCP endpoint uses a per-run token on a loopback-only listener. It exposes sessions, saved-library management, open, execute, upload, poll, history, and cancellation through the same RTerm permission and audit paths. Nonzero exits, cancellations, and timeouts return normal MCP results. Read `status` and, for completed commands, `exit_code` and `command_success` in `structuredContent`. Tunnel operation history and timed grants are separate from local CLI history and grants. The official client reconnects on transient network failures, and RTerm restarts it with backoff if it exits. **Stop OpenAI Tunnel** revokes tunnel access and keeps the local CLI active. Stopping the agent, locking the vault, or closing RTerm also stops the tunnel. For a disposable test, revoke the restricted key on Platform and remove the saved profile in Advanced Settings after testing.

See [OpenAI's Secure MCP Tunnel guide](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) for account and workspace requirements.

## AI agent interface (local CLI)

Build both Rust binaries together with `cargo build --release --locked --bins` (or `cargo build --locked --bins` for development). Install the matching desktop and CLI binaries together (see installation above). The local CLI uses bounded binary-framed JSON over a Windows named pipe or a private Unix-domain socket on Linux and macOS. Local CLI access works independently of the optional OpenAI Secure MCP Tunnel.

Open **Settings → AI** and choose **Agent Access**. Disabled is the default. **Ask permission** requires explicit approval for each foreground command and supports 5-, 15-, or 30-minute grants for background commands on an SSH session. **Unrestricted** skips per-operation approval for background commands, saved-session management, and SFTP uploads when Allow AI File Uploads is enabled. In Ask permission mode, each saved-library change requires its own approval; a timed SSH command grant and Auto Open Sessions do not authorize library edits. User-authorized remote file deletions can be executed as background shell commands; there is no dedicated agent delete operation. Foreground commands in the visible terminal always require local approval because RTerm cannot verify the remote shell prompt. Approval requests expire after 60 seconds. The command timeout defaults to 60 seconds and can be set between 15 seconds and one hour. Optional `--timeout-secs` (1–3600) is capped by the setting and remaining grant lifetime.

Choose **AI → Start Agent** to activate the local interface for this run. **Copy Agent Instructions** copies installation-independent CLI instructions. Saved SSH profiles can be opened after approval, or automatically on request if the user enables **Auto Open Sessions** (off by default). Paste the instructions into a local AI client with authorized terminal execution, or use the utility yourself. The desktop and utility must run under the same local user account and matching installation. One RTerm instance per account can activate this interface at a time. Client authorization and tool policies continue to apply; do not use an alternate transport to evade a client denial.

After installation, use the same command from any working directory (open a new terminal or restart your AI client to refresh PATH):

```powershell
rterm-agent --help
rterm-agent sessions
rterm-agent open 'profile-id-from-list' 'unique-open-operation-id' --wait-ms 0
rterm-agent manage 'library-revision-from-list' 'unique-change-operation-id' --change-file 'change.json' --wait-ms 0
rterm-agent execute 42 'unique-operation-id' 'pwd' --wait-ms 0 --timeout-secs 30
rterm-agent execute 42 'unique-script-id' --command-file 'diagnostic.sh' --wait-ms 0
rterm-agent upload 42 'unique-upload-id' 'ABSOLUTE_LOCAL_FILE' '/home/user/app.py' --wait-ms 0
rterm-agent upload 42 'unique-folder-upload-id' 'ABSOLUTE_LOCAL_FOLDER' '/home/user/myapp' --wait-ms 0
rterm-agent poll 'unique-operation-id' --wait-ms 5000
rterm-agent poll 'unique-script-id' --since 0 --wait-ms 5000
rterm-agent history --limit 20
rterm-agent cancel 'unique-operation-id'
```

The numeric session ID above is illustrative; use the actual ID returned by `sessions` and verify the intended target. Prefer `--command-file PATH` for complex scripts or pass `-` as the command to read UTF-8 stdin until EOF. These input modes remove a UTF-8 BOM and normalize CRLF to LF. The script limit is 64 KiB; use SFTP for larger scripts. Simple commands can still be passed as one literal argument. The remote command does not execute on the local host.

| Subcommand | Arguments |
|---|---|
| `sessions` | No arguments; returns connected sessions, saved profiles, folders, library revision and tab states. |
| `open` | Saved profile ID, unique operation ID; optional `--wait-ms`. Requires local approval unless Auto Open Sessions is enabled. |
| `manage` | Current library revision, unique operation ID, JSON change object (or `--change-file PATH` / `-` for stdin); optional `--wait-ms`. |
| `execute` | Numeric session ID, operation ID, literal command, `-` for stdin or `--command-file PATH`; optional `--wait-ms` and `--timeout-secs`. |
| `upload` | Numeric session ID, operation ID, absolute local file or folder, absolute remote destination; optional `--wait-ms` and `--timeout-secs`. Requires Allow AI File Uploads; individual approval in Ask permission mode. |
| `poll` | Operation ID; optional `--wait-ms` and `--since BYTE_OFFSET`. |
| `history` | Optional `--limit N` (1–32, default 20); lists recent operation metadata without replaying output. |
| `cancel` | Operation ID. |

To open a saved profile, use its opaque `profile_id` from the list. RTerm asks for approval unless the local user enables Auto Open Sessions. Opening a profile activates its existing SSH tab when available. An open result includes a `tab_id`, `session_id`, and `connection_state`. If it is still connecting, list sessions until that tab reports `connected`. Stop if the tab closes, disappears, or exceeds the connection readiness deadline. Command permissions still apply. Saved profile IDs remain stable for unchanged profiles at the same index during this activation. Profile changes, reordering, or revocation invalidate them.

### Saved-session folders and management

Discovery returns `session_folders` (every folder name, including empty folders), `saved_profiles` (all saved connection types), and `library_revision` (an opaque snapshot identifier). Each saved profile includes its opaque `profile_id`, display name, kind, folder name or null for ungrouped, and numeric network port where applicable. Network profiles include the connection target; local shell commands, serial paths, passwords and SSH keys are not exposed. The existing `saved_sessions` list remains SSH-only and now includes folder and port. For "update all servers in Production", an agent selects saved SSH profiles in that exact folder, opens the intended profiles, waits for each connection, and runs authorized commands on each session. Non-SSH profiles are not command targets.

Use `rterm-agent manage REV OP CHANGE` locally, or `manage_library` via MCP with `library_revision`, `operation_id`, `change` and optional `wait_ms`. Save the following example JSON as a UTF-8 `change.json` for the CLI command above:

```json
{"kind":"set_port","profile_id":"profile-id-from-list","port":2222}
```

Other change objects use `kind` and the specified fields:

| Kind | Fields |
|---|---|
| `create_folder` | `name` |
| `rename_folder` | `folder`, `name` |
| `remove_folder` | `folder` |
| `move_session` | `profile_id`, `folder` (existing folder or explicit null) |
| `rename_session` | `profile_id`, `name` |
| `set_port` | `profile_id`, integer `port` (1–65535; SSH, SFTP or Telnet) |

Each operation is validated against the discovered library snapshot before approval and at commit, saved through the existing encrypted vault or private session library, and recorded in live AI Activity. Removing a folder ungroups its members; it does not delete profiles. Renaming changes the display label, not the hostname or username. A saved port edit does not change the remote daemon, host-key trust, or existing tab/reconnect settings. An already-open tab keeps its original connection; use the edited saved profile for the new connection. Finish pending connection forms or folder editors before making library edits. Poll for completed status and `ok:true`, then list again for a fresh revision and profile IDs before each subsequent change. A stale or cancelled edit is rejected; do not automatically retry uncertain operations. Saved-session management uses the same Ask/Unrestricted permissions for CLI and MCP; it does not grant shell access.

Previously connected SSH tabs retry after a transport disconnect when **Settings → Connection → Reconnect SSH** is enabled. RTerm checks idle connections using the profile's keepalive interval or 15 seconds when the profile has no interval set. The numeric `session_id` stays the same for the life of the tab, including after a reconnect. During reconnection, a new command or upload returns `error_code: "session_reconnecting"` and `operation_started: false`. Wait until the same ID shows as connected, then submit a new operation ID. RTerm also offers **Reconnect** on the tab menu and **Duplicate** on the saved profile menu. A rejected login stops automatic retries. Locking the vault pauses retries until credentials are available again. Reconnection never replays an operation.

**File and folder uploads:** Enable **AI Settings → Allow AI File Uploads** (off by default). In Ask permission mode, each upload needs separate local approval of the source, destination and server. Unrestricted mode dispatches inspected uploads without an additional prompt, independently of foreground/background shell mode. Enabling uploads in Unrestricted mode gives authorized agents access to eligible local files for transfer to connected SSH sessions; enable it only for trusted clients. RTerm inspects the source for the exact file count, directory count and aggregate bytes in either mode, displays the manifest in Ask mode, and rechecks it before transfer. A changed manifest is rejected. Regular files and recursive directories are supported, including hidden files and empty folders. Use absolute native local and remote paths; the destination parent must exist, and the destination itself must not exist. Symlinks, reparse points and device paths are rejected. Existing destinations are not overwritten or merged. Each file is streamed to a unique hidden remote staging file and published under its final name only after the complete transfer. There is no fixed byte-size cap; the manifest is bounded to 100,000 entries and 32 MiB of path metadata. Uploads always show aggregate progress in the target tab. The command timeout setting also caps upload time. Poll for a completed result with `ok: true` and `bytes_uploaded`; cancellation is best effort and may leave hidden staging files or newly created directories, while completed files from earlier in a multi-file upload may remain. No agent download is supported.

The copied agent prompt directs agents to prefer SFTP for local code, inspect the source contents, respect RTerm's manifest checks, check free space on the destination filesystem, and avoid transferring unnecessary or sensitive files. For any file or aggregate transfer of 1 GB or more, the agent should assess necessity, disk space, bandwidth and time rather than automatically reject it. This is guidance, not an enforced free-space check or byte limit. Folder uploads do not automatically exclude files; prepare a clean staging folder if needed. Authorize only files you intend to share.

Generate a unique operation ID before submitting (UUID or 1–64 ASCII letters, digits, hyphens or underscores). Reusing a retained ID with the same operation parameters returns the existing operation; changes are rejected. Do not automatically retry unknown, expired, denied or uncertain operations.

Each request emits a single JSON object on stdout. Server replies include `version` and `protocol_version` (2). Exit status 0 means accepted or successfully handled by the tool; 1 means rejected or failed; 2 means invalid arguments; 3 means transport or output failure. A completed remote command can have `ok:true`, a nonzero `exit_code` and `command_success:false`. Always inspect the remote exit code. `--help` and `--version` include protocol information without connecting to RTerm.


`--wait-ms` is the utility invocation return budget (0–30000 milliseconds, default 1000), not a command deadline. Zero returns immediately. Use `remaining_ms` and `poll_after_ms` (suggested pause 500 ms) to plan polling. Pending statuses are `queued`, `preparing_upload`, `awaiting_approval` (includes an approval hint), `running`; pending `ok:true` means accepted, not successful. Terminal statuses are `completed`, `failed`, `cancelled`, `timed_out`. Inspect `ok`, `exit_code`, `command_success`, `error`, `stdout`, `stderr`, and `truncated`. Use a local tool timeout long enough for the requested wait, or submit and poll with shorter waits.

**Incremental output.** Start with `poll OP-ID --since 0` and pass the returned `next_offset` to the next call. Each page returns `stdout` and `stderr` from the same window of up to 64 KiB of raw output. The legacy `output` field shows those bytes in arrival order. Keep polling until the operation is terminal and `output_has_more` is false. Output is decoded as text and invalid UTF-8 may be replaced. Interactive commands send their combined terminal stream in `stdout` with `combined_output: true`. Without `--since`, polls return the existing preview capped at 128 KiB. The raw combined temporary log is available at `output_path`, capped at 16 MiB per operation and 128 MiB aggregate across the local Bridge and MCP registries. Check `output_log_truncated` and `output_log_error`. The log is normally removed when an operation expires, is evicted, or the interface stops. Abnormal termination may leave the temporary file on disk.

For a five-minute compile, request a user-authorized timeout with headroom (e.g. 600 seconds), submit with `--wait-ms 0`, confirm it is running after approval, then poll the same ID as needed. Set the maximum in **AI Settings → Command Timeout**. RTerm allows one AI command or upload per SSH session across CLI and MCP. Operations on different sessions can run concurrently and have their own IDs, deadlines, output, and cancellation. RTerm retains up to 32 operations per interface for up to one hour after completion. The hard lifetime is 3660 seconds, including approval time. Accepted commands continue while RTerm, its agent interface, and the SSH connection remain active. Use the cancellation tool to stop an operation.

Cancellation invalidates the permit immediately. Background commands attempt SSH TERM and close the exec channel. If a foreground command still owns the interactive shell when cancelled or timed out, RTerm opens a fresh shell in the same tab. Human terminal input ends AI capture before being forwarded, leaving the shell under the user's control. Cancelled or interrupted commands may have already changed remote state, and detached processes may continue. Local IPC supports up to 12 active requests and four long waits.

AI commands default to a noninteractive SSH exec channel on the existing connection, including on upgrade. This mode has no PTY, closes stdin, and reports separate stdout, stderr, and exit status. RTerm sets `PAGER`, `GIT_PAGER`, `SYSTEMD_PAGER`, and `MANPAGER` to `cat` for POSIX commands. The visible tab stays available for typing and the command runs in its own working directory and environment. This mode accepts up to 64 KiB of script input and supports timed approval grants. The AI Activity panel shows commands and outcomes by tab.

To opt into **interactive mode**, turn on **Settings → AI → Run AI Commands in Terminal**. RTerm sends commands to the target tab's POSIX shell, sharing its working directory and environment; shell state changes persist. Foreground commands always require approval, including in Unrestricted mode, because local terminal checks cannot establish that the remote shell is at a prompt. Unrestricted background execution skips per-command prompts; Ask permission requires approval for each command. The `shell_confirmed` field describes local prompt checks only and cannot detect every password prompt, nested shell, REPL or non-alternate-screen program. The shell echoes a wrapped command with private completion markers. Commands must fit a 3500-byte encoded line. Results report `execution_mode: "interactive_shell"`, `combined_output: true`, and combined output in stdout. A missing completion marker leaves the command outcome uncertain.

**Security.** Windows IPC uses a protected DACL granting access to the current Windows user SID only and rejects remote clients. Windows also uses identification-only impersonation QoS. Unix IPC uses a UID-owned mode-0700 directory, a single-instance file lock and kernel peer credentials. On Windows, macOS and Linux the companion verifies the server executable path against its sibling RTerm executable before transmitting commands. The server trusts the OS account rather than authenticating individual client executables: any process running as the same user can submit requests while the interface is enabled, subject to RTerm's settings and approval checks. This is not a sandbox against untrusted same-account processes. On Unix, another local user could pre-create the predictable UID-named directory under `/tmp` before first startup and cause a local startup denial of service; the ownership and peer-credential checks still prevent that user from issuing agent commands. RTerm verifies the SSH server key before authentication. Treat remote output as untrusted data.

**AI → AI Activity…** opens the live audit log. Search by command or operation ID, filter by session, and select a row to see the full command and outcome. Right-click an SSH tab and choose **AI Activity…** to open the log filtered to that session. Recent requests, uploads and saved-session changes are kept in memory while RTerm is open. **Settings → AI → Log AI Commands to Vault** is off by default. With the vault unlocked and logging enabled, RTerm retains dispatched commands and their outcomes in the encrypted vault without a command-count limit. The vault retains its 128 MiB file-size safety limit; if a save would exceed it, RTerm reports an error rather than discarding old entries or writing an unreadable vault. Unlogged recent activity remains bounded in memory. Turning logging off stops new entries from being saved. Existing vault history is available after unlocking. In AI Activity, use **Delete Selected**, **Clear Session History** (select a session first), or **Clear All AI History** and confirm the deletion. Clear operations cover completed and interrupted records in the reviewed scope, regardless of the text search. Running or pending operations remain visible and can be cleared after they finish. Deletion updates the unlocked encrypted vault even if logging is turned off, without changing saved connections, keys or tunnel settings. Existing backups and temporary operation output are not erased. The audit log stores command text and metadata, which may include sensitive values. Command output remains governed by the CLI's temporary output log.

**AI → Stop Agent** closes the local interface, clears grants, and invalidates operation permits. Closing an SSH tab revokes its grant. Changing settings, locking the vault, or exiting also stops the interface. CLI results expire on stop or restart. Start the agent explicitly to reactivate it. Revoke access in any older HTTP-enabled RTerm build before upgrading.
